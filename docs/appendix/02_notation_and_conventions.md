This appendix catalogues the notation systems and typographic conventions used
throughout the book. Consistent notation reduces ambiguity when the same concept
appears in formal grammars, IR listings, assembly code, and prose.

## B.1 Mathematical Notation

The following mathematical symbols appear in discussions of formal languages,
automata theory, and dataflow analysis.

| Symbol | Meaning |
|---|---|
| $\Sigma$ | A finite alphabet (set of input symbols) |
| $\Sigma^*$ | The set of all finite strings over alphabet $\Sigma$, including the empty string $\varepsilon$ |
| $\varepsilon$ | The empty string (length zero) |
| $L(G)$ | The language generated by grammar $G$ |
| $\rightarrow$ | Production rule arrow in grammar notation |
| $\Rightarrow$ | Derivation step (one production applied) |
| $\Rightarrow^*$ | Zero or more derivation steps |
| $\text{FIRST}(X)$ | Set of terminals that can begin strings derivable from $X$ |
| $\text{FOLLOW}(A)$ | Set of terminals that can appear immediately after nonterminal $A$ |
| $\sqcup$ | Least upper bound (join) in a lattice |
| $\sqcap$ | Greatest lower bound (meet) in a lattice |
| $\top$ | Top element of a lattice (least informative) |
| $\bot$ | Bottom element of a lattice (most informative / unreachable) |
| $[l, u]$ | Closed interval from $l$ to $u$ |
| $\lfloor x \rfloor$ | Floor function (greatest integer not exceeding $x$) |
| $O(f(n))$ | Asymptotic upper bound (Big-O notation) |
| $\|S\|$ | Cardinality of set $S$ (number of elements) |
| $\in$ | Set membership |
| $\subseteq$ | Subset or equal |
| $\cup$, $\cap$ | Set union and intersection |

## B.2 Grammar Notation

Context-free grammars in this book use BNF-style notation with the following
conventions.

- **Nonterminals** are enclosed in angle brackets: `<izraz>`, `<naredba>`.
- **Terminals** are written in uppercase monospace: `KR_INT`, `PLUS`, `IDN`.
- **Productions** are written with the nonterminal heading on its own line,
  followed by indented alternatives, one per line.
- **Alternation** is implicit: each indented line under a nonterminal heading is
  a separate right-hand side.
- **Epsilon productions** are not used in the parser grammar; optional elements
  are handled by providing separate productions with and without the optional
  component.

In the IR grammar (EBNF), additional notation is used:

| Notation | Meaning |
|---|---|
| `{ X }` | Zero or more repetitions of X |
| `[ X ]` | Optional: zero or one occurrence of X |
| `"keyword"` | Literal keyword string |
| `X \| Y` | Alternative: X or Y |
| `;` | End of production rule |

## B.3 Source Code Conventions

### B.3.1 C Source Language

Source-language identifiers are written in code font: `main`, `count`, `x`.
C keywords appearing in prose are styled identically: `int`, `while`, `struct`.
When a C expression appears inline in text, it is enclosed in backticks:
`a + b * c`. Longer code examples are set in fenced code blocks with the `c`
language annotation.

### B.3.2 Java Implementation

The compiler implementation is written in Java 21 and organized into Maven
modules. The following naming conventions apply throughout the Java codebase:

| Convention | Scope | Example |
|---|---|---|
| Package prefix | All modules | `hr.fer.ppj` |
| Module packages | Per compiler phase | `hr.fer.ppj.lexer`, `hr.fer.ppj.parser`, `hr.fer.ppj.semantic` |
| Class names | PascalCase | `FriscCodeGenerator`, `PipelineRunner`, `IrInterpreter` |
| Method names | camelCase | `emitPrologue()`, `resolveType()`, `performCycle()` |
| Constants | UPPER_SNAKE_CASE | `DEFAULT_TIMEOUT`, `DEFAULT_STEP_LIMIT` |
| Test classes | Suffix `Test` | `LexerTest`, `SemanticAnalyzerTest` |

When Java class names appear in prose, they are written in code font:
`FriscRunner`, `HelperLibrary`. Fully qualified class names are used only when
necessary to disambiguate; otherwise, the simple class name suffices.

## B.4 IR Syntax Conventions

The intermediate representation uses the following naming conventions.

| Element | Convention | Examples |
|---|---|---|
| Temporary | `t` followed by a non-negative integer | `t0`, `t1`, `t42` |
| Block label | Uppercase `L` followed by an integer, or a descriptive name | `L0`, `L3`, `loop_body` |
| Type keyword | Lowercase | `int32`, `char`, `uchar`, `float`, `bool`, `void` |
| Parametric type | Keyword with angle brackets | `ptr<int32>`, `array<char,10>` |
| Struct type | `struct` followed by the tag name | `struct Point` |
| Constant | `#` prefix with explicit type annotation | `#0:int32`, `#'a':char`, `#3.14:float` |
| Null pointer | `null` with type annotation | `null:ptr<int32>` |
| Symbol reference | Scope prefix followed by colon and name | `local:x`, `param:n`, `global:buffer` |
| Section directives | Dotted keywords | `.program`, `.func`, `.frame`, `.slots`, `.blocks` |

### B.4.1 IR Instruction Format

Each IR instruction follows the pattern:

```
tN = opcode operands : result_type
```

The destination temporary appears on the left of the equals sign. The opcode
follows, then its operands (temporaries, constants, or symbol references),
and finally a colon followed by the result type. Instructions without a result
(such as `store`, `jmp`, `br`, `ret`) omit the destination and type suffix.

### B.4.2 IR Block Structure

Blocks are delimited by labels on their own line (e.g., `L0:`) and end with a
terminator instruction (`jmp`, `br`, or `ret`). The first block in a function
is the entry block. Block labels within a function are unique but may be reused
across different functions.

## B.5 FRISC Assembly Conventions

FRISC assembly listings follow the conventions of the FRISCjs assembler.

| Element | Convention | Examples |
|---|---|---|
| Register | Uppercase `R` followed by digit 0--7 | `R0`, `R5`, `R7` |
| Label | Uppercase identifier starting in column 1 | `F_MAIN`, `L_MAIN_L0`, `F_MUL` |
| Instruction | Uppercase mnemonic preceded by whitespace | `ADD`, `LOAD`, `JP` |
| Immediate | Default base is hexadecimal; use `%D` prefix for decimal | `%D 100`, `FF` |
| Pseudoinstruction | Backtick prefix | `` `ORG ``, `` `DW ``, `` `DS ``, `` `EQU `` |
| Comment | Semicolon to end of line | `; initialize SP` |
| Conditional suffix | Appended to jump/call/ret mnemonics | `JP_Z`, `JP_SLT`, `CALL_`, `RET_NZ` |

Numeric literals in generated FRISC assembly always carry an explicit `%D`
prefix when the intended base is decimal, because the FRISCjs assembler defaults
to hexadecimal interpretation for bare numeric literals. Hexadecimal values
appear without a prefix (e.g., `MOVE 40000, R7` means 0x40000 = 262144 decimal).

### B.5.1 Label Naming in Generated Code

The code generator follows a systematic label naming convention:

| Label Pattern | Meaning | Example |
|---|---|---|
| `F_name` | Function entry point | `F_MAIN`, `F_GCD` |
| `L_name_Ln` | Basic block within a function | `L_MAIN_L0`, `L_GCD_L3` |
| `F_MUL`, `F_DIV`, `F_MOD` | Integer helper routines | -- |
| `F_FMUL`, `F_FDIV`, `F_I2F`, `F_F2I` | Q16.16 helper routines | -- |
| `L_BOUNDS_ERROR` | Bounds-check failure handler | -- |
| `G_name` | Global variable | `G_BUFFER`, `G_COUNT` |

### B.5.2 Register Roles

The following register assignments are fixed by the ABI and remain consistent
across all generated code:

| Register | Role | Saved by |
|---|---|---|
| R0--R4 | Scratch / temporaries | Caller |
| R5 | Frame pointer (FP) | Callee |
| R6 | Return value | -- |
| R7 | Stack pointer (SP) | Implicit |

## B.6 Mermaid Diagram Conventions

Diagrams throughout the book are authored in Mermaid notation and rendered to
PDF or SVG during the book generation process. The following conventions apply.

- **Flowcharts** (`flowchart TD` or `flowchart LR`) depict control flow,
  pipeline stages, and architectural overviews.
- **State diagrams** (`stateDiagram-v2`) depict automata, lexer states, and
  execution cycles.
- **Sequence diagrams** (`sequenceDiagram`) depict interactions between
  components such as the CPU and memory during instruction execution.
- Node labels use concise text; detailed explanations appear in the surrounding
  prose.
- Edge labels indicate conditions, data types, or transfer directions.
- All diagrams are enclosed in fenced code blocks with the `mermaid` language
  annotation.

## B.7 Pseudocode Conventions

Pseudocode in this book uses an imperative style with the following elements.

- `procedure name(params):` introduces a named procedure.
- Indentation indicates block structure; no braces or `begin`/`end` keywords.
- `if`, `while`, `for`, `return` have their conventional meanings.
- Assignment uses `=`; equality testing uses `==`.
- Comments begin with `//`.
- Type annotations are omitted unless essential for clarity.
- Array access uses bracket notation: `a[i]`.
- Set operations use standard mathematical notation: $\in$, $\cup$, $\cap$.

## B.8 Error Reporting Convention

All compiler phases report failures with a uniform structure:

1. **Phase identifier** -- which compilation stage detected the error.
2. **Failure reason** -- a concise description of the problem.
3. **Diagnostics** -- source location, relevant token or IR instruction, and
   type information when available.
4. **Remediation hint** -- a suggestion for how to resolve the issue, when
   determinable.

Error reports are written to `errors.txt` in the compiler output directory
(`compiler-bin/` by default). The format is structured to enable both human
reading and automated parsing by test harnesses.

## B.9 Performance Metrics Convention

Performance data throughout this book follows these conventions:

- **Instruction count** is reported as a bare integer representing the total
  number of FRISC instructions executed during a simulation run.
- **Percentages** for instruction breakdown (e.g., "helper calls account for
  45% of execution") refer to the fraction of total instruction count.
- **Optimization impact** is expressed as a reduction percentage relative to
  the O0 (unoptimized) baseline: "O1 reduces instruction count by 18%."
- **Step limits** are stated in their natural units: 200,000,000 for the FRISC
  simulator, 2,000,000 for the IR interpreter.
